# Portfolio Code Guide

This guide explains the portfolio as if you are new to React, TypeScript, Vite, and GitHub Actions. You do not need to understand every line before making a small content change. Start with the file map, change one thing at a time, and run the checks before pushing.

## The shortest mental model

The project has four layers:

1. **Content** lives mainly in `src/portfolioData.ts`.
2. **React components** in `src/` turn that content into HTML.
3. **CSS** in `src/styles.css` controls how the HTML looks at different screen sizes.
4. **Vite** builds those source files into the static `dist/` folder that GitHub Pages publishes.

The browser follows this path when it loads the site:

```text
index.html
    ↓ loads
src/main.tsx
    ↓ renders
src/App.tsx
    ├── reads arrays and objects from src/portfolioData.ts
    ├── renders the hero and impact strip
    └── passes data into section components
            ↓
        React creates browser HTML
            ↓
        src/styles.css styles that HTML
```

The interactive queue lab has one extra path:

```text
slider changes in SignalLab.tsx
    ↓ update React state
simulateQueue(...) in simulation.ts
    ↓ returns metrics, series, and histogram bins
SignalLab.tsx
    ↓ redraws the numbers and chart
browser
```

### Generated or tool-managed files

- `dist/` is generated by `pnpm build`. Do not edit or commit it.
- `node_modules/` contains installed packages. Do not edit or commit it.
- `pnpm-lock.yaml` records exact dependency versions. Commit it when an intentional dependency change updates it.
- `tsconfig*.json` tells TypeScript how to check browser and configuration code.

## React and TypeScript in plain language

A React component is a function that returns JSX. JSX looks like HTML, but it can include JavaScript expressions inside braces:

```tsx
function Greeting({ name }: { name: string }) {
  return <p>Hello, {name}.</p>;
}
```

The object after the function name is the component's input, called **props**. The TypeScript part (`{ name: string }`) says that `name` must be text. TypeScript checks this while developing; it does not add anything visible to the page.

Several portfolio components use `.map(...)` to turn an array into repeated cards:

```tsx
{items.map((item) => (
  <article key={item.id}>{item.title}</article>
))}
```

`key` helps React match each rendered card with its data when something changes. It should be stable and unique within that list.

`as const` and `readonly` in `portfolioData.ts` tell TypeScript that content should be treated as fixed data. They prevent a component from accidentally changing shared content while the page is running.

## How content reaches the page

`src/portfolioData.ts` exports structured data. `src/App.tsx` imports it and passes each collection to the component that knows how to display it:

```tsx
<FeaturedWork items={featuredWork} />
<ExperienceTimeline items={experienceTimeline} />
<CapabilityMap groups={capabilityGroups} />
<EducationContact education={education} links={externalLinks} />
```

This separation is intentional:

- data files answer **what should the page say?**
- components answer **what HTML structure should represent it?**
- CSS answers **how should that structure look?**

Keeping those responsibilities separate makes wording updates safer and makes layouts reusable.

## Common edits

### Change a job, project, skill, or contact link

Open `src/portfolioData.ts` and find the matching exported array or object. Preserve the existing field names and punctuation around the object.

For example, an external link follows this shape:

```ts
{
  id: "github",
  label: "GitHub",
  href: "https://github.com/GerardZhou",
  kind: "profile",
},
```

After changing a link, click it in the local preview. A syntactically valid URL can still lead to the wrong page.

### Change the headline or top-of-page metrics

Open `src/App.tsx`:

- `proofPoints` drives the four-number impact strip.
- `evidenceRows` drives the systems-profile panel.
- the `<section className="hero">` block contains the main headline and introduction.

Keep every public metric precise and supportable. Do not publish confidential implementation details merely to make a description sound more technical.

### Change colors, spacing, or typography

Open `src/styles.css`. The custom properties near `:root` are the best starting point for site-wide colors and shared values. Search for the class name from the relevant component to find more specific styling.

The media queries near the end adjust layouts for smaller screens. After a visual change, check at least:

- a wide desktop window;
- a narrow mobile-sized window;
- keyboard focus using the Tab key; and
- reduced motion if you changed transitions or animation.

### Change the order of sections

Move the corresponding component calls in `src/App.tsx`. Section numbers such as `01`, `02`, and `03` are written into the section components, so update those labels too if the new order changes their meaning.

Do not casually change section `id` values such as `selected-work` or `experience`. Navigation and evidence links use those IDs as anchors.

### Add a selected-work item

1. Add the new identifier to the `FeaturedWorkId` union in `src/portfolioData.ts`.
2. Add a complete object to `featuredWork` using an existing object as the shape reference.
3. Use `visibility: "public"` only when the URL is genuinely public and safe to share.
4. Add relevant evidence links in `capabilityGroups` if the project proves a listed skill.
5. Run the checks and inspect the card on both desktop and mobile.

### Change the interactive lab

Presentation belongs in `src/SignalLab.tsx`; mathematical/model behavior belongs in `src/simulation.ts`.

The lab uses a fixed random seed, so the same inputs produce the same outputs. That repeatability makes the demo easier to explain and test. If you change formulas, limits, stability thresholds, or event ordering, add or update a focused test in `src/simulation.test.ts` before changing the interface copy.

The lab is deliberately described as a synthetic educational model. Do not relabel its output as production telemetry or a real-world benchmark.

## Accessibility choices worth preserving

- `index.html` includes a skip link so keyboard users can bypass navigation.
- Sections use real headings in order instead of styled generic text.
- Form controls in the lab use labels and descriptions.
- Charts have accessible titles/descriptions, while purely decorative graphics use `aria-hidden="true"`.
- Focus styles remain visible for keyboard navigation.
- the reduced-motion media query removes nonessential motion for users who request it.

When adding a new interactive element, use a native HTML element (`button`, `a`, `input`) whenever possible. Native elements already provide keyboard and assistive-technology behavior that a clickable `div` does not.

## Run the site locally

Requirements:

- Node.js 22.13 or newer
- Corepack, which is included with supported Node.js installations

Install the exact dependencies recorded in the lockfile:

```bash
corepack enable pnpm
corepack install --global pnpm@11.7.0
pnpm install --frozen-lockfile
```

Start the development server:

```bash
pnpm dev
```

Vite prints a local URL, usually `http://localhost:5173/`. The development page refreshes after saved source edits.

Before pushing, run:

```bash
pnpm lint
pnpm test
pnpm build
pnpm preview
```

What each command does:

- `pnpm lint` catches suspicious TypeScript and React patterns.
- `pnpm test` runs deterministic unit tests once.
- `pnpm build` runs TypeScript checks and creates the production `dist/` folder.
- `pnpm preview` serves that production folder locally so you test what will actually be deployed.

If `pnpm dev` is already running, stop it with <kbd>Control</kbd>+<kbd>C</kbd> in its terminal.

## Adding a résumé later (opt-in)

There is no résumé in the repository or website by default. That reduces the chance of publishing a private phone number, address, stale document, hidden PDF metadata, or confidential work detail.

When you intentionally want to publish one:

1. Make a copy of the final PDF and review the copy page by page.
2. Check both visible text and PDF metadata. Remove anything you do not want publicly downloadable or searchable.
3. Rename the reviewed copy to `Gerard-Zhou-Resume.pdf`.
4. Put it in `public/Gerard-Zhou-Resume.pdf`. Vite copies `public/` files to the root of `dist/`, so the eventual public URL will be `/Gerard-Zhou-Resume.pdf`.
5. In `src/portfolioData.ts`, add `"resume"` to `ExternalLinkId` and add `"document"` to the `ExternalLink` `kind` union. Then add this object to `externalLinks`:

   ```ts
   {
     id: "resume",
     label: "Résumé",
     href: "/Gerard-Zhou-Resume.pdf",
     kind: "document",
   },
   ```

   Because `EducationContact` maps over `externalLinks`, this automatically creates a link in the contact section.
6. If you also want a header link, add this property to `linkById` in `src/App.tsx`:

   ```ts
   resume: externalLinks.find((link) => link.id === "resume")!,
   ```

   Then render an anchor with `href={linkById.resume.href}` in the header. Copy the structure of another external link so its icon, `target`, and `rel` behavior stay consistent.
7. Run the full validation commands.
8. From `pnpm preview`, click every résumé link and confirm the correct reviewed PDF opens.
9. Open `dist/Gerard-Zhou-Resume.pdf` directly and confirm its contents one final time.
10. Use `git status --short` to verify that you are committing only the intended document and code changes.

To unpublish it, delete `public/Gerard-Zhou-Resume.pdf`, remove the `externalLinks` entry, remove any manually added header lookup/link, and rebuild before pushing.

## How GitHub Pages deployment works

This is a **user site**, so the repository must be named exactly `GerardZhou.github.io`. Its public root URL is `https://gerardzhou.github.io/`, which is why `vite.config.ts` uses `base: "/"`.

Every push to `main` starts `.github/workflows/deploy.yml`:

1. GitHub creates a clean Ubuntu runner.
2. The workflow checks out the repository and installs the configured Node and pnpm versions.
3. It installs exactly the dependencies in `pnpm-lock.yaml`.
4. It runs linting, tests, and the production build.
5. Only if all checks pass, it uploads `dist/` as a Pages artifact.
6. The deployment job publishes that artifact through GitHub Pages.

First-time setup:

1. Create a public repository named `GerardZhou.github.io` under the `GerardZhou` account.
2. Push this project to its `main` branch.
3. Open **Settings → Pages** and select **GitHub Actions** as the source if needed.
4. Open **Actions** and inspect the **Deploy portfolio to GitHub Pages** run.
5. After it succeeds, visit `https://gerardzhou.github.io/` and test navigation, external links, mobile layout, and the queue lab.

If deployment fails, open the failed Actions run and expand the first red step. Fix that underlying lint, test, install, or build error locally before pushing again.

## A safe editing routine

For most updates, this small loop is enough:

1. Run `git status --short` so you know the starting state.
2. Make one focused edit.
3. Inspect it with `pnpm dev`.
4. Run lint, tests, and the production build.
5. Review `git diff` and check every public link.
6. Commit with a message that says what changed and why.
7. Push, watch the Actions run, and verify the live page.

Small, focused changes are easier to understand, test, review, and undo than a large batch of unrelated edits.
